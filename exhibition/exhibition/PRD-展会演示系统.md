## 1. 需求背景

### 1.1 为什么要做这个系统

我们团队有两个核心产品需要联合展示：

1. **SeeDance**：一个 AI 视频生成平台（Java 后端），用户输入文字描述，AI 自动生成视频
2. **启元 T1 机器人**：一台从启元（Primebot）购买的人形机器人，需要进行二次开发

在即将到来的展会（20-30 家企业参展，观众包含政府高官）中，我们需要把这两个产品**联合起来演示**：参观者对机器人说话，机器人理解后调用 SeeDance 平台生成视频，生成完毕后自动在屏幕上播放。

### 1.2 为什么需要一个专门的展示页面

机器人和 SeeDance 平台本身都有各自的界面，但它们**不是为展会场景设计的**：

- SeeDance 的后台管理界面是给运营人员用的，不够美观、不够直观
- 机器人本身没有大屏展示能力
- 展会观众（尤其是政府高官）需要看到一个**正式、美观、有科技感**的展示界面
- 需要把「对话」「进度」「视频播放」三个信息**整合在一块屏幕上**同时展示

### 1.3 展会现场条件

| 条件 | 说明 |
|---|---|
| 展位 | 标准展位，与其他 20-30 家企业相邻 |
| 屏幕 | 主办方提供（尺寸和分辨率未知，需适配 1080p-4K） |
| 电脑 | **我们自带笔记本电脑**，通过 HDMI 连接主办方屏幕 |
| 网络 | 展会 WiFi（可能不稳定） |
| 观众 | 不特定人群，包括政府高官，每人在展位停留 1-5 分钟 |
| 噪音 | 展馆环境嘈杂，语音识别可能受影响 |

### 1.4 核心挑战

1. **展会 WiFi 不可靠** → 必须有离线兜底方案
2. **观众停留时间短** → 演示流程不能太长，需要有「快速展示」模式
3. **环境嘈杂** → 语音识别可能失败，需要备用输入方式
4. **面向政府高官** → UI 必须正式、高端、有科技感，不能花哨
5. **多企业竞争注意力** → 视觉效果必须第一眼就吸引人

## 2. 产品概述

### 2.1 一句话描述

> 一个运行在笔记本浏览器上的全屏 Web 页面，通过 HDMI 输出到展会大屏，实时展示「访客语音 → 机器人对话 → AI 视频生成进度 → 视频自动播放」的完整流程。

### 2.2 系统组成

```
┌─────────────────────────────────────────────────────────────┐
│                        展会现场                              │
│                                                             │
│  ┌──────────┐  HDMI   ┌──────────────┐  WiFi  ┌─────────┐ │
│  │ 笔记本    │────────►│ 主办方屏幕    │        │SeeDance │ │
│  │          │         │ (大屏展示)    │        │云服务器  │ │
│  │ · 浏览器  │         └──────────────┘        └────┬────┘ │
│  │ · 控制程序│                                      │      │
│  └─────┬────┘                                      │      │
│        │ USB/网络                                   │      │
│        ▼                                           │      │
│  ┌──────────┐                                      │      │
│  │ 启元 T1   │──────── HTTP 调用 ──────────────────┘      │
│  │ 机器人    │                                             │
│  └──────────┘                                             │
└─────────────────────────────────────────────────────────────┘
```

### 2.3 本 PRD 覆盖范围

本文档**只覆盖展示页面（Web 前端）**的需求。以下不在本文档范围内：

| 组件 | 负责方 | 说明 |
|---|---|---|
| SeeDance Java 后端 API | 后端团队 | 视频生成接口，本页面通过 HTTP 调用 |
| 机器人 Python 控制程序 | 机器人团队 | 语音识别、动作控制、API 调用 |
| 演示状态查询接口（HTTP 轮询） | 后端团队 | 展示页面每 0.5 秒轮询「对话内容 + 任务状态 + 视频地址」，替代原 WebSocket 推送方案 |

## 3. 用户角色与使用场景

### 3.1 用户角色

| 角色 | 描述 | 与系统的交互方式 |
|---|---|---|
| **展会观众** | 路过展位的人，可能是政府高官、企业代表、普通参观者 | 对机器人说话（语音），观看大屏展示 |
| **操作员**（你） | 我们团队的人，负责控制演示流程 | 在笔记本上通过**隐藏控制面板**操作 |
| **机器人** | 启元 T1，负责语音交互和身体动作 | 把访客说的话与生成任务提交给后端；展示页面通过轮询后端获取这些消息 |

### 3.2 核心使用场景

**场景 A：正常演示（有网络）**

```
观众走到展位 → 对机器人说「帮我生成一个30秒的视频」
→ 大屏左侧显示对话气泡
→ 大屏右侧显示生成进度（排队→生成→渲染→完成）
→ 进度完成后自动播放视频
→ 播放结束回到待机画面
```

**场景 B：操作员手动控制**

```
操作员按 ~ 键呼出控制面板
→ 输入文字模拟观众说的话
→ 按回车，页面开始演示完整流程
→ 可以随时跳转到任意阶段
→ 演示完毕后点「重置」回到待机
```

**场景 C：断网兜底（离线模式）**

```
展会 WiFi 断开
→ 底部状态栏自动变红显示「离线」
→ 操作员切换到离线 Demo 模式
→ 页面播放预录好的完整演示视频
→ 观众无法分辨是在线还是离线
```

**场景 D：循环展示（无人互动时）**

```
展位没有人
→ 大屏播放待机动画（粒子效果 + 产品介绍）
→ 吸引路人驻足
→ 有人靠近时操作员启动演示流程
```

## 4. 功能需求

### 4.1 页面布局（全屏四区域）

页面采用 **CSS Grid** 全屏布局，分为四个区域：

```
┌─────────────────────────────────────────────────────┐
│                  ① 顶部品牌栏 (72px)                  │
├────────────────────┬────────────────────────────────┤
│                    │                                │
│  ② 左侧对话区      │      ③ 右侧主展示区              │
│     (380px)        │        (自适应剩余宽度)          │
│                    │                                │
├────────────────────┴────────────────────────────────┤
│                  ④ 底部状态栏 (48px)                  │
└─────────────────────────────────────────────────────┘
```

### 4.2 ① 顶部品牌栏

| 元素 | 说明 |
|---|---|
| 左侧 Logo | SeeDance 品牌标识，金色渐变圆角方块 + 字母「S」 |
| 左侧品牌名 | 「SeeDance」，金色渐变文字 |
| 中间分隔线 | 竖线分隔符 |
| 中间产品名 | 「启元 T1 · AI 视频生成系统」 |
| 右侧徽章 | 「展会演示模式」，金色边框胶囊标签 |
| 右侧时钟 | 实时时间，格式 HH:MM:SS，每秒更新 |

**设计细节：**
- 背景：深蓝半透明 + 毛玻璃模糊（`backdrop-filter: blur(20px)`）
- 底部边框：金色半透明 1px 线
- 高度：固定 72px

### 4.3 ② 左侧对话区

**功能：** 实时显示访客和机器人之间的对话，类似聊天界面。

| 元素 | 说明 |
|---|---|
| 区域标题 | 「实时对话」，金色大写字母，下方小字「Live Conversation · 语音交互记录」 |
| 消息列表 | 可滚动区域，新消息自动滚到底部 |
| 访客消息 | 靠左对齐，青色（`#00d4ff`）标签「访客 Visitor」，青色边框气泡 |
| 机器人消息 | 靠右对齐，金色标签「T1 机器人」，金色边框气泡 |
| 输入指示器 | 机器人「正在输入」时显示三个跳动的金色圆点 |
| 时间戳 | 每条消息右下角显示 HH:MM |

**消息动画：**
- 新消息从下方滑入（`translateY(12px) → 0`），持续 0.4 秒
- 使用 `cubic-bezier(.16,1,.3,1)` 缓动曲线（弹性效果）

**滚动条：**
- 宽度 3px，金色半透明，不突兀

### 4.4 ③ 右侧主展示区

主展示区有 **四个状态**，同一时间只显示一个：

#### 状态 A：待机画面

| 元素 | 说明 |
|---|---|
| 旋转环 | 180px 圆环，双色（金+蓝）旋转动画，4秒一圈 |
| 内旋转环 | 第二层圆环，反向旋转，3秒一圈 |
| 中心图标 | 🎬 电影图标，带金色发光阴影 |
| 标题 | 「AI VIDEO GENERATION」，28px，字间距 6px，浅灰色 |
| 描述 | 「向机器人说出您的视频需求 / AI 将在数分钟内为您生成专属视频作品」 |
| 呼吸灯 | 底部一个青色小圆点，2秒周期呼吸动画 |

#### 状态 B：生成进度

| 元素 | 说明 |
|---|---|
| 标题 | 「VIDEO GENERATING」 |
| 进度环 | 220px SVG 圆环，渐变描边（青→金），带发光效果 |
| 百分比数字 | 圆环中心，52px 超大字号，实时更新 |
| 阶段标签 | 百分比下方小字：排队中 / 生成中 / 渲染中 / 完成 |
| 四阶段指示器 | 横向排列的四个节点 + 连接线 |
| 详情文字 | 底部一行描述当前具体操作（如「正在渲染建筑与光影效果...」） |

**四阶段指示器详细：**

```
  ●──────────●──────────●──────────●
 排队中      生成中      渲染中      完成
(灰色)    (青色发光)   (灰色)     (灰色)
           ↑当前阶段
```

- 未到达阶段：灰色圆点 + 灰色文字
- 当前阶段：青色发光圆点 + 青色文字 + 外发光阴影
- 已完成阶段：金色圆点 + 金色文字
- 连接线：已完成段显示金色渐变，未完成段显示深灰

**进度更新节奏（进度条完全由前端模拟，与真实生成进度无关）：**

> ⚠️ **真实视频生成时长未知**（可能几十秒，也可能几分钟）。因此进度条**不能按固定时间跑到 100%**——否则会出现「进度显示完成、但真实视频还没生成好，页面无视频可播」的穿帮。
> **策略**：假进度快速推进到 **95% 后停住并循环微动**（进度环缓慢呼吸），同时持续轮询后端；一旦轮询返回「视频已就绪」，立刻跳 100% → 完成态 → 播放真实视频。这样既体现老板要的「快」，又能吸收任意长度的真实等待。

| 时间 | 进度 | 阶段 | 详情文字 |
|---|---|---|---|
| 0s | 0% | 排队中 | 正在连接 SeeDance 云端服务... |
| 4s | 8% | 排队中 | 任务已提交，排队等待中... |
| 8s | 20% | 生成中 | AI 模型正在分析视频描述... |
| 12s | 35% | 生成中 | 正在生成视频关键帧... |
| 16s | 50% | 生成中 | AI 正在构建场景结构... |
| 20s | 65% | 生成中 | 正在渲染建筑与光影效果... |
| 24s | 80% | 渲染中 | 正在生成视频运动轨迹... |
| 28s | 90% | 渲染中 | 正在进行画质增强处理... |
| 32s | 95% | 渲染中 | 正在合成最终视频画面... |
| 32s 之后 | 95%（保持） | 渲染中 | 视频即将完成，正在做最后处理...（进度环缓慢呼吸，**持续轮询等待真实视频就绪**，时长未知也不穿帮） |
| 轮询命中就绪 | 100% | 完成 | 视频生成完成！ |

#### 状态 C：生成完成

| 元素 | 说明 |
|---|---|
| 勾选图标 | 80px 金色圆环 + 内部勾选 SVG，弹入动画 |
| 标题 | 「视频生成完毕」，24px，金色 |
| 描述 | 「即将自动播放，请稍候...」 |

显示约 3 秒后自动切换到视频播放状态。

#### 状态 D：视频播放

| 元素 | 说明 |
|---|---|
| 视频播放器 | HTML5 `<video>` 标签，全屏填充，`object-fit: contain` |
| 底部遮罩 | 渐变半透明黑色遮罩（从透明到 80% 黑） |
| 左下角标签 | 「SeeDance AI Generated」，金色胶囊标签 |
| 右下角提示 | 「视频播放完毕后自动返回待机」 |

视频播放结束后 3 秒自动回到待机画面。

### 4.6 隐藏控制面板（操作员专用）

**这是操作员用来控制演示流程的工具，观众看不到。**

```
│ │ 帮我生成一个海边日落视频 ×│ │

```

#### 4.6.3 功能说明

| 功能 | 操作 | 效果 |
|---|---|---|
| **发送指令** | 输入文字 → 回车或点击按钮 | 模拟访客说了这句话，启动完整演示流程 |
| **自动演示** | 点击按钮 | 用默认台词「你好，请帮我生成一个30秒的AI视频，主题是未来城市」启动流程 |
| **阶段跳转** | 点击对应按钮 | 直接跳到指定阶段的画面（跳过中间过程） |
| **历史记录** | 点击任意历史条目 | 用该条目的文字重新启动演示 |
| **删除单条** | 悬停历史条目 → 点 × | 删除该条历史 |
| **清空历史** | 点击按钮 | 清空所有历史记录 |
| **重置全部** | 点击按钮 | 清空对话、停止所有定时器、回到待机画面 |

#### 4.6.4 历史记录持久化

- 存储位置：浏览器 `localStorage`
- 存储键名：`seedance_exhibition_history`
- 最大条数：30 条（超出自动删除最旧的）
- 去重逻辑：相同文字不重复存储，但会更新到最新位置
- 刷新/关闭浏览器后历史不丢失
- 三款页面（V1/V2/V3）共享同一份历史

### 6.3 数据流

> **通信方案：HTTP 轮询（原 WebSocket 方案已废弃）。** 页面每 0.5 秒向后端查一次「演示状态」，后端把机器人提交的对话、SeeDance 任务状态、生成好的视频地址一并返回。相比 WebSocket 常驻连接，轮询在展会弱网下更抗断线、后端实现更简单，代价仅是最多 0.5 秒的推送延迟——而这点延迟完全被假进度条吸收，观众无感知。（0.5 秒间隔请求量很小，单页面每 2 秒仅 4 次请求，后端压力可忽略。）

#### 在线模式（真实对接）

```
访客说话
   │
   ▼
机器人程序(Python) ──HTTP──► SeeDance Java API
   │                          POST /api/v1/generate   提交生成，返回 taskId
   │
   └──把「访客说的话 + taskId」提交给后端演示接口
              POST /api/v1/demo/submit
                        │
                        ▼
                 后端维护「当前演示状态」
                 （对话 / 任务阶段 phase / 视频地址 / 轮次 round）
                        ▲
                        │ 每 0.5 秒轮询
                        │
   展示页面(浏览器) ─────┘
      GET /api/v1/demo/state
        │
        ├── 发现新一轮对话（round 变化）→ 左侧加气泡，启动假进度动画
        ├── 假进度推进到 95% 后停住循环，持续轮询等待
        ├── 轮询返回 phase=ready + videoUrl → 跳 100% → 完成态(约3s) → 播放真实视频
        ├── 轮询返回 phase=failed → 提示失败并切预录兜底视频（V1.2）
        └── 视频播完 → 回到待机，等待下一轮
```

**「必须生成完视频才进入下一轮」**：以后端 `round`（轮次号）为准——只有当前轮 `phase=ready` 且视频播放结束，页面才回到待机接受下一轮；后端在上一轮未结束前对新的 `submit` 直接拒绝或排队，避免多轮并发导致画面穿帮。

#### 离线模式（本地测试 / 断网兜底，纯前端模拟，不依赖后端）

```
控制面板输入文字（或点「自动演示」）
    │
    ▼
JavaScript 定时器序列
    │
    ├── 0.8s → 添加访客消息
    ├── 1.6s → 显示输入指示器
    ├── 3.0s → 添加机器人回复
    ├── 4.2s → 切换到进度画面
    ├── 5.5s~32s → 假进度推进到 95%
    ├── 32s 之后 → 停在 95% 保持（本地测试可设一个假的「就绪」时间点触发下一步）
    ├── 就绪 → 切换到完成画面（约 3s）
    └── 之后 → 播放视频（本地为预录 demo 视频）
```

### 6.4 轮询接口协议（HTTP，与后端对接）

采用两个 HTTP 接口：**机器人/操作员提交请求** + **页面轮询状态**。进度百分比不再由后端下发，全部由前端模拟（后端只负责告诉页面「视频好了没、地址是多少」）。

**① 提交生成请求（机器人程序 / 控制面板手动输入 → 后端）**

```
POST /api/v1/demo/submit
Body: { "text": "帮我生成一个海边日落的视频" }
```

- **机器人只交访客的原话**（`text` 一个字段），不需要提供机器人回复、不碰 SeeDance。
- **机器人的回话采用后端固定话术**（2026-10-08 决策）：后端收到 submit 后，自动往本轮 `messages` 追加一条写死的 `bot` 回复（如「好的，我已收到您的请求，正在为您生成视频，请稍候。」），机器人侧无需生成对话。
- 后端收到后：`round` +1、`phase` 置 `generating`、`messages` 写入「访客原话 + 固定 bot 回复」，并调用 SeeDance `POST /api/v1/generate` 提交生成、记录 taskId。上一轮未结束时可直接拒绝或排队（见 §6.3）。

> 完成时的那句 bot 提示（「视频已生成完毕！即将为您播放…」）由**前端页面自己追加**（见 `onVideoReady()`），后端 `messages` **不要**再下发这条，避免重复气泡。

**② 轮询演示状态（展示页面 → 后端，每 0.5 秒一次）**

```
GET /api/v1/demo/state
```

返回：

```json
{
  "round": 5,                       // 轮次号，变化即代表新一轮开始
  "phase": "generating",            // idle | generating | ready | failed
  "messages": [                     // 本轮对话，页面据此渲染左侧气泡
    { "role": "user", "text": "帮我生成一个30秒的视频", "time": "14:32" },
    { "role": "bot",  "text": "好的，正在为您生成…",       "time": "14:32" }
  ],
  "videoUrl": null                  // phase=ready 时给出真实视频地址，其余为 null
}
```

**页面处理规则：**

| 轮询结果 | 页面动作 |
|---|---|
| `round` 变化且 `phase=generating` | 渲染 `messages` 对话气泡，启动假进度动画（推进到 95% 后保持） |
| `phase=ready` 且 `videoUrl` 非空 | 进度跳 100% → 完成态（约 3s）→ 播放 `videoUrl` |
| `phase=failed` | 显示生成失败提示，切预录兜底视频（V1.2 资源就绪后） |
| `phase=idle` | 保持 / 回到待机画面 |

> `videoUrl` 若是 SeeDance 的临时签名地址需注意有效期——建议后端在 `phase=ready` 时返回**新鲜可播**的地址，页面拿到后立即播放、不缓存复用。

| 屏幕宽度 | 布局调整 |

| ≥ 1200px | 完整布局：左侧对话 380px + 右侧展示区 |
| 900-1200px | 左侧对话缩窄到 320px |

### 6.6 三方联调分工与接口契约

采用**方案 A：后端做中转站**（后端已具备 SeeDance 对接能力）。三方职责单一、互不直连——机器人只写后端、页面只读后端，两边从不直接通信。

```
访客说话
   │  ①语音转文字（机器人自有能力）
   ▼
机器人(Python) ──②POST /demo/submit {text}──► 后端(Java，中转站/白板)
                                                 │  ③调 SeeDance 生成（后端已有）
                                                 │  ④维护 round/phase/messages/videoUrl
                                                 │  ⑤生成好后 phase=ready + videoUrl
   展示页面(浏览器) ──⑥每0.5秒 GET /demo/state──┘
        └──⑦据状态渲染：冒对话气泡 / 假进度到95%保持 / ready后跳100%播放
```

**分工表：**

| 角色 | 必须提供 / 负责 | 明确不用管 |
|---|---|---|
| **机器人（Python）** | ① 访客语音转文字；② 调后端 `POST /api/v1/demo/submit`，body 只含 `{ "text": "访客原话" }` | ❌ 不碰 SeeDance ❌ 不管进度/视频地址 ❌ 不生成对话回复（用后端固定话术）❌ 不管页面渲染 |
| **后端（Java）** | ③ 收到 submit 后调 SeeDance 生成、记录 taskId；④ 维护演示状态（`round`/`phase`/`messages`/`videoUrl`）；⑤ 收到访客话后追加**固定 bot 话术**到 `messages`；⑥ 提供 `GET /api/v1/demo/state`；⑦ 生成完成后置 `phase=ready` 并填**新鲜可播**的 `videoUrl`，失败置 `phase=failed` | ❌ 不管前端动画节奏（进度条由前端模拟） |
| **展示页面（前端）** | 把 `CONFIG.mode` 改 `live`、`pollUrl` 填后端地址；每 0.5 秒轮询 state 并按 §6.4 规则渲染；完成提示气泡由前端自行追加 | ❌ 不直连机器人 ❌ 不直连 SeeDance |

**两个接口契约（唯一对接面）：**

| 接口 | 方向 | 用途 | 详见 |
|---|---|---|---|
| `POST /api/v1/demo/submit` | 机器人 → 后端 | 提交访客原话，触发一轮生成 | §6.4 ① |
| `GET /api/v1/demo/state` | 页面 → 后端（0.5s 轮询） | 读取当前轮次/阶段/对话/视频地址 | §6.4 ② |

**联调顺序（可分步、不被任何一方卡住）：**

1. **前端 ↔ 后端**：后端先按契约提供 `submit`/`state`（生成可先用假视频地址占位），前端 `mode=live` 指向后端，跑通「提交→轮询→渲染→播放」。
2. **模拟机器人**：机器人未就绪时，用任意 HTTP 工具（或脚本）手动 `POST /demo/submit {"text":"..."}` 冒充机器人，即可驱动整条链路，无需等机器人。
3. **接入机器人**：机器人把语音识别结果按同一 `submit` 契约发出，替换第 2 步的手动提交。
4. **接真实 SeeDance**：后端把占位视频地址换成 SeeDance 真实生成结果，全链路打通。

> 关键约定：`round` 只在**上一轮结束**（视频播完回待机 / 或后端超时清理）后才接受新一轮 submit，避免多轮并发导致画面错乱（§6.3）。

### A.4 如何对接真实后端

当前页面使用**模拟数据**（JavaScript 定时器）。对接真实后端改为**轮询**，步骤：

1. 保留 `runDemo()` 里的假进度定时器，但改成「推进到 95% 后停住保持」，不再固定跑到 100%
2. 启动一个每 0.5 秒执行一次的轮询：`GET /api/v1/demo/state`（后端部署在服务器上，见 §6.3）
3. 轮询发现 `round` 变化 / 有新 `messages` → 调用 `addMsg()` 渲染对话
4. 轮询返回 `phase=ready` → `setProgress(100)` → 切完成态 → 用 `videoUrl` 播放视频
5. 轮询返回 `phase=failed` → 显示失败提示 / 切预录兜底
6. 视频播放结束 → 停止本轮处理，回到待机等待下一轮

详见 §6.4 轮询接口协议。
