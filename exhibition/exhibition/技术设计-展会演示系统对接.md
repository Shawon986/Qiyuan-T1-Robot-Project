## 1. 目标与范围

### 1.1 目标
把「访客语音 → 机器人对话 → SeeDance 生成视频 → 大屏自动播放」串成一条可现场演示的链路，核心诉求是**快**（进度体验流畅、不穿帮）与**稳**（弱网可用、失败可兜底）。

### 1.2 本文档范围
覆盖三方对接的**技术设计**：架构、接口契约、前后端职责、状态机、异常兜底、部署、安全、联调与排期。

### 1.3 非目标
- 前端视觉/动画细节（见 PRD §4/§5，原型已实现）。
- SeeDance 生成能力本身（后端已有对接）。
- 机器人语音识别算法（机器人团队自有能力）。

## 2. 架构总览

### 2.1 系统上下文（L1）
四个参与方，**互不直连**，全部经后端中转站解耦：

| 参与方 | 技术栈 | 归属 | 职责一句话 |
|---|---|---|---|
| 展会访客 | — | — | 对机器人说话 |
| 机器人 | Python | 机器人团队 | 语音转文字 → 提交给后端 |
| 后端中转站 | Java | 后端团队 | 调 SeeDance + 维护演示状态 + 提供接口 |
| 展示页面 | HTML/JS | 前端（你） | 轮询状态 → 渲染大屏 |
| SeeDance | 外部平台 | — | 真实生成视频 |

### 2.2 容器视图（L2）与数据流
详见 `diagrams/integration-flow.dot`。核心链路：

```
访客说话 →①机器人语音转文字 →②POST /demo/submit{text}
  → 后端：round+1 / phase=generating / 追加固定bot话术 / 调 SeeDance 生成
  → 后端轮询 SeeDance 任务，好了回填 phase=ready + videoUrl
页面每0.5s GET /demo/state → handleState 渲染（对话/进度/播放）
```

### 2.3 为什么是「中转站」而非直连
浏览器页面**无法被动接收**推送（除非 WebSocket）。采用轮询后，页面只能主动拉取，故必须有一个后端持有的「演示状态」作为唯一数据源。机器人写、页面读，两边不直接通信——这也是弱网下最稳的形态（详见 §3）。

## 3. 通信方案选型

| 维度 | HTTP 轮询（选定） | WebSocket（废弃） |
|---|---|---|
| 观众感知延迟 | ≤0.5s，被假进度吸收，无感 | 秒推 |
| 弱网稳定性 | **高**：单次失败下次自动重来 | 一般：断连需重连/心跳 |
| 后端实现成本 | **低**：两个普通 HTTP 接口 | 高：连接管理、重连、心跳 |
| 出错面 | 小 | 大 |

**结论**：真实瓶颈是视频生成耗时（未知，可能数分钟），0.5s 轮询延迟完全可忽略；展会弱网下轮询「打不死」的特性更重要。故选轮询。

## 4. 接口契约（唯一对接面）

### 4.1 提交生成请求 `POST /api/v1/demo/submit`
- **方向**：机器人 → 后端（本地调试时也可由脚本/工具冒充机器人调用）。
- **请求体**：
  ```json
  { "text": "帮我生成一个海边日落的视频" }
  ```
  机器人**只交访客原话一个字段**；不提供机器人回复、不碰 SeeDance。
- **后端处理**：
  1. 校验 `text` 非空、长度上限（建议 ≤200 字）。
  2. 并发控制：上一轮未结束（`phase != idle`）时，**拒绝（返回 409）或排队**，`round` 不自增（见 §7.4）。
  3. `round += 1`；`phase = generating`；`messages = [{role:user,text,time}, {role:bot,text:固定话术,time}]`。
  4. 异步调 SeeDance `POST /api/v1/generate`，记录 taskId。
- **固定 bot 话术（2026-10-08 决策，后端写死）**：`"好的，我已收到您的请求，正在为您生成视频，请稍候。"`
- **响应**：`{ "round": 5, "accepted": true }`（拒绝时 `accepted:false` + 原因）。

### 4.2 轮询演示状态 `GET /api/v1/demo/state`
- **方向**：展示页面 → 后端，每 0.5s 一次。
- **响应体**：
  ```json
  {
    "round": 5,
    "phase": "generating",            // idle | generating | ready | failed
    "messages": [
      { "role": "user", "text": "帮我生成一个海边日落的视频", "time": "14:32" },
      { "role": "bot",  "text": "好的，我已收到您的请求，正在为您生成视频，请稍候。", "time": "14:32" }
    ],
    "videoUrl": null                   // phase=ready 时为新鲜可播地址，其余 null
  }
  ```
- **字段说明**：

  | 字段 | 类型 | 含义 |
  |---|---|---|
  | `round` | int | 轮次号，变化即新一轮开始（页面据此清空重渲染）|
  | `phase` | enum | `idle` 待机 / `generating` 生成中 / `ready` 视频就绪 / `failed` 失败 |
  | `messages` | array | 本轮对话，`role` ∈ user/bot；页面按序渲染气泡 |
  | `videoUrl` | string\|null | 仅 `ready` 时非空 |

- **约定**：完成时的提示气泡（「视频已生成完毕…」**由前端页面自行追加**（`onVideoReady()`），后端 `messages` **不要**下发这条，避免重复气泡。

### 4.3 页面处理规则（已实现于 `handleState()`）

| 轮询结果 | 页面动作 |
|---|---|
| `round` 变化且 `phase=generating` | 清空并渲染 `messages`，启动假进度（爬到 95% 保持）|
| `phase=ready` 且 `videoUrl` 非空 | 跳 100% → 完成态(约3s) → 播放 `videoUrl` |
| `phase=failed` | 显示失败提示 → 回待机（V1.2 接预录兜底）|
| `phase=idle` | 保持/回到待机 |
| 请求失败（网络/5xx）| 状态栏标红「后端不可达」，不崩溃，下次轮询自动恢复 |

## 5. 前端设计（已实现，`v1-command-center.html`）

### 5.1 演示状态机
详见 `diagrams/frontend-state.dot`：
```
待机 → 生成中(假进度0→95%) → 95%保持(呼吸循环) → 完成100% → 完成态3s → 播放 → 待机
                                     └→ 失败 → 待机
```

### 5.2 关键设计：假进度「95% 保持」
真实生成时长**未知**，故进度条**不能按固定时间跑到 100%**（否则卡在「完成」却无视频可播，穿帮）。策略：
- `startFakeProgress()`：约 28s 内把假进度从 0 爬到 95%，逐段切换详情文案。
- `enterHold()`：到 95% 后在 95↔96% 轻微呼吸、循环切换「即将完成」文案，**持续等待真实就绪信号**，时长未知也不穿帮。
- `onVideoReady(url)`：收到 `ready` 才跳 100% → 完成 → 播放。

### 5.3 模式开关（`CONFIG`）
```js
const CONFIG = {
  mode: 'local',            // 'local' 纯前端模拟 | 'live' 轮询后端
  pollUrl: '/api/v1/demo/state',
  pollInterval: 500,        // 0.5s
  autoReadyMs: 0,           // local 模式：>0 自动就绪；0=手动点「模拟视频就绪」
  fakeVideo: '...'
};
```
对接后端时**只改 `mode='live'` + `pollUrl`**，其余逻辑不动。

### 5.4 健康探测
`live` 模式下，系统状态灯由**轮询是否成功**驱动（`pollOnce` 成功→在线，失败→「后端不可达」标红），比 `navigator.onLine` 准（后者识别不了「连上WiFi但无外网」）。`local` 模式仍用 `navigator.onLine`。

## 6. 后端设计（待开发）

> **定位：独立的大屏演示模块，完全不计费、不核算。** 不碰 `WalletService`/`settlementService`，不写 `usage_record`/`billing_txn`，因此**不复用带计费的 `GenerationService.submitVideo`**（它含预扣/结算 + 10s 上限校验）。改为**直连 provider 层纯生成能力**，仿现成的免计费范本 `ChannelAdminService.testChannel`。

### 6.1 演示状态存储
- 状态量极小：`{round, phase, messages, videoUrl, upstreamTaskId}`。
- **存储用 Redis**：MorAI 生产为**双实例 8081/8082**（§10.7），进程内存会导致轮询命中不同实例读到不一致状态，故必须放共享存储。
- 生命周期：一轮结束（页面播完回待机 / 或超时）后清 `phase=idle`。

### 6.2 SeeDance 生成对接（免计费路径，复用 provider 层）
- 调用链（绕过整条计费链）：
  ```
  channelRouteService.route(model)              // 选渠道
  → GenerationChannelResolver.videoProvider(channel)
  → videoProvider.submitVideo(new VideoRequest(model, prompt, duration, ratio, null), context(channel))  // 拿 upstreamTaskId
  轮询: videoProvider.queryVideo(upstreamTaskId, ctx) 直到 terminal()
  → SUCCEEDED: phase=ready, videoUrl=task.urls()[0]
  → FAILED:    phase=failed
  ```
- 凭据由 `ai_channel.apiKeyEnc` 解密（现成），**无需价格配置、无需 sys_config**。
- 后端**自己轮询上游任务**（`@Scheduled` 每 5s + `ScheduledJobLock` 多实例去重，仿 `GenerationPollJob` 但**不结算**），完成后回填状态。
- `videoUrl` **走转存中转，不直连上游**：实现时发现 `VideoTask` 硬约定「上游 URL 绝不外露用户，须转存我方中转」，故 SUCCEEDED 后经 `GenerationTransferService.transfer(ownerUserId,"video",urls)` 转存，取 `MediaFileRef.accessUrl()`（`LocalDiskMediaStorage` = **免登录下载路由**，未登录大屏可直接播；OSS = 签名 URL）。`ownerUserId` 用专用 demo owner（不计费，仅决定 `media_file.user_id`）。

### 6.3 固定话术
bot 回复由后端写死（§4.1），机器人不参与对话生成。

### 6.4 并发与轮次控制
`round` 只在上一轮结束后才接受新 submit，避免多轮并发导致画面错乱（§7.4）。

### 6.5 时长与生成参数（2026-10-08 决策）
- **时长固定默认 15s**（配置项 `morai.demo.video-duration`，可调），**不解析访客口语里的秒数**——访客只说「给我生成一段视频」，那句原话整体当 `prompt`。
- **比例固定 16:9**（配置项，适配大屏横屏）。
- **模型走配置项** `morai.demo.video-model`（部署时填具体 SeeDance 2.5 模型标识，不写死代码）。
- **SeeDance 2.5 能力（官方文档已核实，2026-10-08）**：单次请求**最长 30s**；官方**原生支持"多轮续写延长(extend over multiple rounds)"与首帧/尾帧(`role:first_frame`/`last_frame`)、`return_last_frame`**。
  - ⚠️ **本 demo 实时链路只用单次 ≤30s（默认 15s），不使用续写**——续写=多次串行生成=分钟级耗时，与"快"冲突。
  - **>30s 长片走离线预生成**（现场当结果播放/待机宣传片），不做实时续写。
  - 现有 `BytePlusAdapter.submitVideo` 仅发 `text`+可选 `image_url`，**不含** `first_frame`/`last_frame`/`return_last_frame`/extend；若将来要续写，需先扩适配器（本期不做）。

## 7. 异常与兜底

| # | 场景 | 处理 |
|---|---|---|
| 7.1 | 后端不可达 / 5xx | 页面状态栏标红「后端不可达」，保持当前画面，轮询自动重试恢复 |
| 7.2 | 生成失败 | 后端置 `phase=failed`；页面 `onDemoFailed()` 提示并回待机；V1.2 切预录兜底视频 |
| 7.3 | `videoUrl` 过期/加载失败 | `<video>` `onerror` 兜底（V1.2：切预录）；后端保证 ready 时地址新鲜 |
| 7.4 | 多轮并发（上一轮没完又来新访客）| 后端拒绝或排队，`round` 不乱增；页面只认后端 `round` |
| 7.5 | 展会断网 | 页面切离线标识；操作员用控制面板本地模拟演示（`mode=local`）或播放预录视频 |
| 7.6 | 生成超长（数分钟）| 95% 保持吸收等待；操作员可控制面板手动跳转，或后端设超时上限置 failed |

## 9. 安全

1. **SeeDance 密钥只在后端**，不下发前端/机器人（选方案 A 的核心安全理由）。
2. **submit 接口防护**：加简单鉴权/令牌 + 限流，防止现场被恶意刷提交（虽内网风险低）。
3. **XSS**：页面 `addMsg()` 当前用 `innerHTML` 拼接文本；访客语音转写内容不可信，**建议改为 `textContent` 或对 text 转义**，避免特殊字符注入（见 §12 待办）。
4. 状态接口只读、无敏感数据；`videoUrl` 若含签名注意时效与日志脱敏。

## 10. 联调计划（可分步、不被任一方卡住）

1. **前端 ↔ 后端**：后端先按契约提供 `submit`/`state`（`videoUrl` 可先用假地址占位），前端 `mode=live` 指向后端，跑通「提交→轮询→渲染→播放」。
2. **模拟机器人**：机器人未就绪时，用 HTTP 工具/脚本手动 `POST /demo/submit {"text":"..."}` 冒充机器人驱动全链路。
3. **接入机器人**：机器人把语音识别结果按同一 submit 契约发出，替换第 2 步手动提交。
4. **接真实 SeeDance**：后端把占位地址换成真实生成结果，全链路打通。
5. **现场彩排**：大屏 + HDMI + 弱网/断网兜底演练。
